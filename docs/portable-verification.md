# Проверка portable-релиза SIZCardGenerator

## 1. Когда требуется проверка

Если задача предусматривает актуальный portable-релиз, пересобрать и проверить его после изменения кода, зависимостей сборки, `data/norms.xlsx`, `templates/card_template.xlsx`, `app_icon.ico`, `version_info.txt`, `SIZCardGenerator.spec` или build-скриптов. Изменение только документации не требует сборки. Внешние нормы и шаблон можно обновлять без перекомпиляции EXE, но выпуск полного актуального комплекта проверяется по этой процедуре.

## 2. Проверка перед сборкой

- Из корня проекта выполнить `git status` и `git branch --show-current`; сверить ветку с задачей (обычно `main`) и убедиться в отсутствии неожиданных изменений. Ожидаемые изменения задачи не требуют автоматического коммита.
- Проверить наличие `app.py`, `siz_card_generator/generator.py`, `requirements.txt`, `requirements-dev.txt`, `data/norms.xlsx`, `templates/card_template.xlsx`, `app_icon.ico`, `version_info.txt`, `SIZCardGenerator.spec`, `build_exe.bat` и `build_exe.ps1`.
- Убедиться, что проверки затронутого поведения исходников завершены. Зафиксировать SHA-256 норм и шаблона для проверки их неизменности при сборке и тестах.
- Закрыть используемую сборку. Сохранить нужные пользовательские данные вне `build`, `dist` и `release/SIZCardGenerator`: скрипт полностью удаляет эти каталоги. Тесты проводить в отдельной копии релиза.

## 3. Сборка

При необходимости установить зависимости: `python -m pip install -r requirements-dev.txt`.

Из корня проекта запустить `build_exe.bat`. Он вызывает `build_exe.ps1`, который выполняет PyInstaller по `SIZCardGenerator.spec` и формирует `release/SIZCardGenerator`. Дождаться успешного завершения; при ошибке не считать оставшиеся файлы готовым релизом.

## 4. Проверка структуры релиза

В `release/SIZCardGenerator` должны присутствовать:

```text
SIZCardGenerator.exe
_internal/
data/norms.xlsx
templates/card_template.xlsx
output/
output/backups/
requests/
```

Сразу после сборки `output` (включая `backups`) и `requests` должны быть пустыми. Переносить всю папку приложения, включая `_internal`, а не только EXE.

## 5. Обязательные Tcl/Tk-компоненты

`_internal/_tcl_data` и `_internal/_tk_data` обязательны для текущей Tkinter/PyInstaller-сборки. Их нельзя удалять при оптимизации размера релиза. Без `_tcl_data` приложение не находит `init.tcl`, без `_tk_data` не находит `tk.tcl` и не открывает главное окно.

Эти библиотеки сценариев автоматически включает hook PyInstaller для Tkinter. DLL Tcl/Tk и дополнительные модули в `_internal/tcl8` не являются их заменой.

## 6. Сравнение внешних ресурсов

После сборки сверить проектные и релизные `data/norms.xlsx` и `templates/card_template.xlsx`. Для задач с изменением этих файлов обязательно сравнить SHA-256 обеих копий; тот же способ рекомендуется для любой сборки:

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath data/norms.xlsx, release/SIZCardGenerator/data/norms.xlsx
Get-FileHash -Algorithm SHA256 -LiteralPath templates/card_template.xlsx, release/SIZCardGenerator/templates/card_template.xlsx
```

Хеши каждой пары должны совпадать. После тестов повторить проверку: сборка и работа приложения не должны менять нормы или шаблон. Не закреплять в инструкции хеш одной версии файла.

## 7. Проверка GUI

- Запустить EXE из отдельной тестовой копии и проверить главное окно, загрузку подразделений и должностей из её `data/norms.xlsx`.
- Проверить «Очистить форму»: очищаются данные работника и ссылка на последнюю карточку, печать отключается; подразделение и должность сохраняются.
- Проверить «Открыть папку карточек» и «Открыть папку заявок»: открываются `output` и `requests` тестовой копии.
- Открыть форму заявки. Проверить обязательные поля, сохранение XLSX в `requests`, активацию «Открыть заявку» только после сохранения и открытие последнего созданного файла. «Закрыть» закрывает форму и сохраняет файл; поля решения специалиста остаются пустыми. Заявка не изменяет нормы.

## 8. Проверка генерации карточки

Выбрать существующую точную пару `Подразделение + Должность`, заполнить обязательные поля синтетическими данными с уникальным табельным номером. Проверить создание XLSX в `output`, листы `Лицевая сторона` и `Оборотная сторона`, данные работника и перечень СИЗ именно выбранной пары. Пустые количества не должны заменяться предполагаемыми значениями; фактическая выдача и возврат остаются для ручного заполнения.

Отдельно ввести отсутствующую пару: GUI должен отклонить её, новая карточка не должна появиться. Не изменять нормы ради отрицательного теста. Не использовать приблизительное сопоставление или перенос СИЗ с другой должности.

## 9. Microsoft Excel Print Preview

При доступном Microsoft Excel открыть созданную карточку кнопкой «Печать карточки СИЗ» и проверить настоящий Print Preview:

- лицевая сторона занимает одну страницу, оборотная одну, всего две;
- области печати охватывают нужные данные, текст и таблицы не обрезаны;
- нет неожиданных header/footer и текста «Подготовлено с использованием системы КонсультантПлюс» на обеих страницах.

Excel необходим для встроенного Print Preview/печати, но базовая генерация XLSX выполняется через `openpyxl` без Excel. Если Excel недоступен, явно отметить проверку печати как невыполненную; программное чтение XLSX не заменяет визуальную проверку. Не отправлять документ на физический принтер для проверки предварительного просмотра.

## 10. Иконка и Windows metadata

Проверить ресурсы PE `ICON` и `GROUP_ICON` и соответствие изображения текущему `app_icon.ico`. Проверить значки EXE, окна и панели задач Windows; наличие ресурсов само по себе не подтверждает видимый значок.

Во вкладке «Свойства → Подробно» сверить `FileDescription`, `ProductName`, `FileVersion`, `ProductVersion`, `LegalCopyright`, `OriginalFilename`, а также доступные `CompanyName` и `InternalName` с текущим [version_info.txt](../version_info.txt). Не копировать значения версий в эту инструкцию. Поля, которые оболочка не показывает, проверить чтением version resource EXE; строковые версии и числовые поля `FixedFileInfo` проверять отдельно.

## 11. Проверка запуска вне проекта

При полном релизном тесте скопировать всю папку `SIZCardGenerator` в отдельный доступный каталог вне проекта. Запустить её EXE с рабочим каталогом, отличным и от корня проекта, и от каталога EXE. Проверить загрузку ресурсов, создание карточки и заявки рядом с этой копией. Это проверяет независимость от проектных абсолютных путей и текущего рабочего каталога.

## 12. Очистка после тестов

Закрыть тестовые окна и файлы. Удалить только созданные в ходе проверки карточки, заявки, диагностические файлы (включая тестовые предупреждения) и временные копии. Перед рекурсивным удалением проверить полный путь временной копии. Не удалять пользовательские данные из реальных рабочих копий. Основной релиз оставить без тестовых результатов.

## 13. Финальная проверка Git

```text
git diff --check
git status
```

Для задачи только на пересборку исходники не должны неожиданно измениться. В отчёте перечислить выполненные проверки, ошибки и недоступные проверки, результаты сравнения ресурсов и состояние Git. Не создавать git commit и не выполнять git push без явного указания пользователя. Основные проектные правила: [AGENTS.md](../AGENTS.md).
